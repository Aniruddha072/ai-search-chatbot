## What we learned
- The original plan (Gradio + Hugging Face Spaces) was reversed *before* any Gradio-specific code was written, by checking HF's current docs live rather than trusting training-time knowledge: creating a Gradio Space on a personal account now requires a paid PRO plan, directly conflicting with the explicit "no money" requirement. Streamlit Community Cloud, checked the same way, is genuinely free for a public GitHub-connected app.
- `bootstrap.py`'s module-level `from ...ragas_evaluator import RagasEvaluator` would have silently broken the whole demo: `ragas_evaluator.py` imports `ragas`, which `requirements.txt` deliberately excludes, so importing `bootstrap.py` itself (needed for `build_demo_pipeline()` too) would have required `ragas` to be installed. Caught by checking what the demo's dependency list excludes against what the composition root actually imports, before deploying - fixed by moving the import inside `build_chat_pipeline()`'s own function body.
- The real architectural finding of the phase: reusing one cached pipeline (`st.cache_resource`) across Streamlit reruns, with one `asyncio.run()` per turn, crashes on a session's *second* question - `RuntimeError: Event loop is closed` - because `GroqClient`/`TavilyProvider`'s async HTTP clients bind to whichever event loop is running when first used, and `asyncio.run()` tears its loop down on return. Reproduced first in isolation with a two-line `httpx.AsyncClient` script before touching the real app, confirmed the fix (fresh clients built and used entirely inside one `asyncio.run()` call, repeated per turn) the same way, then verified live through the actual running app: two real consecutive questions in one browser session, no crash, no errors in the server log.
- `st.write_stream()` - the built-in, seemingly obvious way to stream `PipelineStream` into the UI - turned out to be unusable here for two independent reasons, both found by reading Streamlit's own source rather than assuming: its internal async-to-sync conversion spins up a second, separate event loop (the same cross-loop crash, one level deeper), and it only accepts an actual async generator (`inspect.isasyncgen`), not an arbitrary `__aiter__`-implementing object like `PipelineStream`. Streaming by hand into a placeholder sidesteps both, at the cost of the built-in typewriter animation.
- `streamlit run` puts the script's own directory on `sys.path[0]`, not the invocation `cwd` - unlike `python -m src.presentation.cli`, which relies on `-m` putting the invocation cwd on the path. This broke the app's `from src...` imports immediately on first run; fixed with a small, commented `sys.path` insertion rather than reorganizing the package layout or adding project-wide packaging changes for one entry point.
- A cosmetic, pre-existing (not new) content-quality issue surfaced during live testing: one real Tavily result's title for a Germany-capital query was a raw scraped social-media caption fragment rather than a clean page title. This is the same kind of source-quality variance the CLI already exposes today, not a Streamlit-specific bug - no issue filed, matching the standing bug-tracking workflow's exclusion for expected/environment-level noise rather than a genuine defect.

## Key design decisions
See `docs/decisions.md`, Decisions 14.1-14.3, for the full reasoning behind the hosting pivot, the `NullEvaluator`/`build_demo_pipeline()` split, and the per-turn-fresh-pipeline fix (including why the more "obvious" cached-pipeline design and `st.write_stream()` both had to be ruled out empirically, not just in theory).

## Challenges faced
The event-loop-reuse bug (Decision 14.3) was the one real structural surprise of the phase - a design that looked correct on paper (cache the expensive pipeline object, stream tokens with Streamlit's own built-in helper) failed specifically on a session's *second* turn, which a one-question smoke test would never have caught. Verifying it with an isolated two-line reproduction before touching the real app - and verifying the fix the same way - kept the debugging cheap and conclusive rather than guessing against the full Streamlit + pipeline stack directly.
