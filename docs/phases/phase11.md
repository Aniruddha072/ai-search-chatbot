## What we built
- `src/domain/interfaces.py`: `LLMProvider` gained a third abstract method, `generate_stream(prompt, *, system_prompt=None) -> AsyncIterator[str]` - declared as a plain `def`, not `async def`, since the concrete implementation is an async generator function and calling one returns an async generator object directly, not a coroutine.
- `src/infrastructure/llm/groq_client.py`: `generate_stream()` implemented via `stream=True`, verified against a real live Groq call first (chunk text lives at `chunk.choices[0].delta.content`, empty on the first chunk, `None` on the last). Retry only wraps *acquiring* the stream, never iteration over already-yielded chunks (Decision 11.2).
- `src/application/answer_generator.py`: citation-parsing logic extracted into a shared `_build_answer()` static method, used by both the existing `generate()` and the new `generate_streaming()`. New `StreamedAnswer` class wraps the chunk stream - async-iterate it for text as it arrives, call `build_answer()` afterward for the final citation-parsed `Answer`, one Groq call either way (Decision 11.1). Each chunk wait is individually timeout-bounded rather than the whole stream sharing one budget (Decision 11.3).
- `src/application/pipeline.py`: the validation/planning/search/dedup/rank/context prefix shared by `handle()` and the new `handle_streaming()` was factored into a private `_prepare()`. New `PipelineStream` class mirrors `handle()`'s two outcomes: `.streaming()` wraps an in-progress `StreamedAnswer` and attaches evaluation once consumed; `.completed()` wraps an already-final degraded `Answer` (invalid input / zero sources) with nothing left to stream but its own message text. A generation failure mid-stream is *not* caught here (Decision 11.4) - it propagates to whoever's consuming the stream.
- `src/presentation/cli.py` (new): the interactive loop. Reads stdin via `asyncio.to_thread(input, ...)`, streams the answer to stdout as it arrives, prints sources and RAGAS scores once done, and treats empty/oversized input as an ordinary question that flows through to `ChatPipeline`'s own validation rather than being special-cased in the presentation layer. Ctrl-C/EOF caught around the loop for a clean "Goodbye." instead of a traceback.
- Tests: `test_groq_client.py` gained 5 streaming cases (happy path, acquisition-retry, acquisition-exhaustion, non-transient-no-retry, mid-stream-no-retry) using fakes shaped to match the verified real `groq.AsyncStream` chunk format. `test_answer_generator.py` gained 5 (chunk-by-chunk yielding, citation parsing after consumption, streaming/non-streaming parity on identical text, chunk-timeout propagation, mid-stream-exception propagation). `test_pipeline.py` gained 4 (`handle_streaming` parity with `handle()` on the grounded-answer, zero-sources, invalid-input, and full-context-evaluation cases). Two new gated real-API integration tests (`test_answer_generator.py`, `test_pipeline.py`) stream against live Groq/Tavily.

## What we learned
- Verified a real Python constraint before designing around it: an `async def` function containing `yield` can only `return` with no value - `return some_value` inside an async generator is a `SyntaxError`, confirmed with a two-line script. This directly shaped the `StreamedAnswer` wrapper-object design rather than trying to make a bare generator "return" the final `Answer`.
- Verified Groq's real streaming chunk shape with a live call before writing `GroqClient.generate_stream()`: `stream=True` returns `groq.AsyncStream`, `chunk.choices[0].delta.content` is `''` on the very first chunk and `None` on the last - both worth filtering out, not just falsy-checking casually.
- A real end-to-end CLI run surfaced a small, expected cosmetic issue: `configure_logging()`'s INFO-level handler writes to the same `stdout` the streamed answer prints to, so log lines (Groq/Tavily HTTP request logs, `instructor`'s own init logs) interleave with the prompt and output. They never land *inside* a streamed answer's tokens (nothing in the touched code logs mid-stream), so it's a noise problem, not a correctness one - worth a mention for Phase 13 (Observability & polish), not something to fix here.

## Key design decisions
See `docs/decisions.md`, Decisions 11.1-11.4, for the full reasoning:
- 11.1: `StreamedAnswer` wrapper object, not a bare async generator, because of the verified `return`-in-async-generator constraint.
- 11.2: retry only wraps stream acquisition, never mid-stream iteration - avoids duplicating already-visible output.
- 11.3: per-chunk timeout, not one overall stream timeout - a healthy long answer shouldn't be cut off the way a stalled one should.
- 11.4: `handle_streaming()` doesn't catch generation failures the way `handle()` does - by the time a mid-stream failure happens, some of the real answer may already be visible, so there's nothing honest left to silently replace it with.

## Challenges faced
Adding a third abstract method to `LLMProvider` broke every existing fake/stub implementation across three test files (`test_query_planner.py`, `test_answer_generator.py`, `test_pipeline.py` - including inline classes defined inside individual test functions) with `TypeError: Can't instantiate abstract class ... without an implementation for abstract method 'generate_stream'`. Caught immediately by running the full unit suite rather than assuming the new method wouldn't ripple outward; each fake got a minimal `generate_stream` stub (mostly `raise NotImplementedError` + an unreachable `yield`, to keep it a valid async generator function without ever being exercised in tests that don't care about streaming).
