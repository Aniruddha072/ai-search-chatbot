# Phase 11 — CLI Presentation Layer

**Commit:** `0f07c7d` (feat) / `06bb30a` (docs)

## What we built
- `src/domain/interfaces.py`: `LLMProvider` gained a third abstract method, `generate_stream(prompt, *, system_prompt=None) -> AsyncIterator[str]` - declared as a plain `def`, not `async def`, since the concrete implementation is an async generator function and calling one returns an async generator object directly, not a coroutine.
- `src/infrastructure/llm/groq_client.py`: `generate_stream()` implemented via `stream=True`, verified against a real live Groq call first (chunk text lives at `chunk.choices[0].delta.content`, empty on the first chunk, `None` on the last). Retry only wraps *acquiring* the stream, never iteration over already-yielded chunks (Decision 11.2).
- `src/application/answer_generator.py`: citation-parsing logic extracted into a shared `_build_answer()` static method, used by both the existing `generate()` and the new `generate_streaming()`. New `StreamedAnswer` class wraps the chunk stream - async-iterate it for text as it arrives, call `build_answer()` afterward for the final citation-parsed `Answer`, one Groq call either way (Decision 11.1). Each chunk wait is individually timeout-bounded rather than the whole stream sharing one budget (Decision 11.3).
- `src/application/pipeline.py`: the validation/planning/search/dedup/rank/context prefix shared by `handle()` and the new `handle_streaming()` was factored into a private `_prepare()`. New `PipelineStream` class mirrors `handle()`'s two outcomes: `.streaming()` wraps an in-progress `StreamedAnswer` and attaches evaluation once consumed; `.completed()` wraps an already-final degraded `Answer` (invalid input / zero sources) with nothing left to stream but its own message text. A generation failure mid-stream is *not* caught here (Decision 11.4) - it propagates to whoever's consuming the stream.
- `src/presentation/cli.py` (new): the interactive loop. Reads stdin via `asyncio.to_thread(input, ...)`, streams the answer to stdout as it arrives, prints sources and RAGAS scores once done, and treats empty/oversized input as an ordinary question that flows through to `ChatPipeline`'s own validation rather than being special-cased in the presentation layer. EOF caught around the loop for a clean "Goodbye." instead of a traceback - Ctrl-C's equivalent handling shipped in this phase but turned out not to actually work; see "Post-launch fix 2" below.
- Tests: `test_groq_client.py` gained 5 streaming cases (happy path, acquisition-retry, acquisition-exhaustion, non-transient-no-retry, mid-stream-no-retry) using fakes shaped to match the verified real `groq.AsyncStream` chunk format. `test_answer_generator.py` gained 5 (chunk-by-chunk yielding, citation parsing after consumption, streaming/non-streaming parity on identical text, chunk-timeout propagation, mid-stream-exception propagation). `test_pipeline.py` gained 4 (`handle_streaming` parity with `handle()` on the grounded-answer, zero-sources, invalid-input, and full-context-evaluation cases). Two new gated real-API integration tests (`test_answer_generator.py`, `test_pipeline.py`) stream against live Groq/Tavily.

## What we learned
- Verified a real Python constraint before designing around it: an `async def` function containing `yield` can only `return` with no value - `return some_value` inside an async generator is a `SyntaxError`, confirmed with a two-line script. This directly shaped the `StreamedAnswer` wrapper-object design rather than trying to make a bare generator "return" the final `Answer`.
- Verified Groq's real streaming chunk shape with a live call before writing `GroqClient.generate_stream()`: `stream=True` returns `groq.AsyncStream`, `chunk.choices[0].delta.content` is `''` on the very first chunk and `None` on the last - both worth filtering out, not just falsy-checking casually.
- A real end-to-end CLI run surfaced a small, expected cosmetic issue: `configure_logging()`'s INFO-level handler writes to the same `stdout` the streamed answer prints to, so log lines (Groq/Tavily HTTP request logs, `instructor`'s own init logs) interleave with the prompt and output. They never land *inside* a streamed answer's tokens (nothing in the touched code logs mid-stream), so it's a noise problem, not a correctness one - worth a mention for Phase 13 (Observability & polish), not something to fix here.

## Key design decisions
See `docs/decisions.md`, Decisions 11.1-11.6, for the full reasoning:
- 11.1: `StreamedAnswer` wrapper object, not a bare async generator, because of the verified `return`-in-async-generator constraint.
- 11.2: retry only wraps stream acquisition, never mid-stream iteration - avoids duplicating already-visible output.
- 11.3: per-chunk timeout, not one overall stream timeout - a healthy long answer shouldn't be cut off the way a stalled one should.
- 11.4: `handle_streaming()` doesn't catch generation failures the way `handle()` does - by the time a mid-stream failure happens, some of the real answer may already be visible, so there's nothing honest left to silently replace it with.
- 11.5: a blank-message exception (e.g. a bare `asyncio.wait_for` `TimeoutError()`) is caught and surfaced with its type name instead of silently collapsing into an empty, falsy error string - see "Post-launch fix 1" below.
- 11.6: Ctrl-C handling moved from inside `main()`'s coroutine to wrap `asyncio.run(main())` itself, in a new `run()` - see "Post-launch fix 2" below.

## Challenges faced
Adding a third abstract method to `LLMProvider` broke every existing fake/stub implementation across three test files (`test_query_planner.py`, `test_answer_generator.py`, `test_pipeline.py` - including inline classes defined inside individual test functions) with `TypeError: Can't instantiate abstract class ... without an implementation for abstract method 'generate_stream'`. Caught immediately by running the full unit suite rather than assuming the new method wouldn't ripple outward; each fake got a minimal `generate_stream` stub (mostly `raise NotImplementedError` + an unreachable `yield`, to keep it a valid async generator function without ever being exercised in tests that don't care about streaming).

## Post-launch fix 1: silent evaluation failures
Dogfooding the real CLI against live APIs (immediately after this phase shipped) surfaced a genuine bug, not just the expected logging noise above: a RAGAS evaluation that timed out (`EvaluationService`'s `asyncio.wait_for` budget exceeded, itself caused by the Groq SDK's own internal 429-retry backoff on `RagasEvaluator`'s separate, unwrapped client - Decision 8.5) raised a bare `TimeoutError()`. Verified directly: `str(TimeoutError())` is `''`. That empty string flowed into both the log line and `EvaluationResult.error`, and since an empty string is falsy, `cli.py`'s original `if evaluation.error:` check treated the failure as if it never happened - nothing printed to the log or the terminal at all, even though the non-blocking-evaluation design (Decision 1.6) was otherwise working exactly as intended.

Fixed in both places (Decision 11.5): `EvaluationService` falls back to `type(exc).__name__` when `str(exc)` is blank, and `_print_evaluation()` checks `is not None` instead of truthiness. Verified two ways before committing: 5 new unit tests (`test_evaluation_service.py` x2, `test_cli.py` x3 relevant to this fix, of 5 added there total) proving the exact mechanism, plus a standalone script (not committed) driving the real `ChatPipeline`/`EvaluationService`/`cli._print_evaluation` wiring end-to-end with a fake evaluator raising `TimeoutError("")` and zero network calls - confirmed `(evaluation unavailable: TimeoutError)` now renders instead of silence.

## Post-launch fix 2: Ctrl-C crashed with a raw traceback (GitHub issue #2)

This is also where a new standing project workflow got adopted: discover → reproduce → decide if it's worth a GitHub issue → file the issue *before* fixing → fix → regression test → verify → commit (referencing the issue) → close. `gh` (GitHub CLI) was installed and authenticated for the first time to support it.

Pressing Ctrl-C while `cli.py` sat idle at the prompt crashed with a raw `KeyboardInterrupt`/`CancelledError` double traceback instead of the "Goodbye." this phase's own code claimed to deliver. Root-caused from a real traceback obtained by asking for it directly, not guessed: the exception delivered into `main()`'s coroutine at its current await point is `asyncio.CancelledError`, not `KeyboardInterrupt` - `asyncio.run()` cancels the running task on interrupt, then re-raises the actual `KeyboardInterrupt` from its own top-level frame (`asyncio.Runner.run()`, documented CPython 3.11+ behavior), after `main()` has already been torn down. No `try/except` inside `main()`'s own coroutine, anywhere, could ever catch that - it's raised by a different, outer function once the coroutine no longer exists, not a timing accident.

Notably, 14 automated reproduction attempts (a piped-stdin child process, then a genuine new Win32 console with real `CTRL_C_EVENT` delivery) never triggered the crash - consistent with this being a known class of CPython asyncio/signal-timing race rather than something forceable on demand, not evidence against the bug. The real, first-hand traceback from the user's own terminal was treated as authoritative over the automated harness's failure to reproduce it.

Fixed (Decision 11.6): the `if __name__ == "__main__":` block was extracted into a `run()` function that wraps `asyncio.run(main())` in its own `try/except KeyboardInterrupt:` - the only scope that actually receives the re-raised interrupt. The now-dead in-coroutine handlers were removed (`except EOFError` alone remains where `except (EOFError, KeyboardInterrupt)` used to be - EOF is a normal, non-signal exception and that half of the original handling was always real). Verified via a deterministic regression test (`test_run_exits_cleanly_on_keyboard_interrupt`, forcing the exact mechanism via a monkeypatched `asyncio.run`) plus the user's own live Ctrl-C test against the fix - clean exit, no traceback.

Tracked as GitHub issues #1 (an overly detailed first draft, superseded) and #2 (the concise version actually fixed against); both closed.
